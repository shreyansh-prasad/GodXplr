GodXplr — Research Report
Prepared 3 Nov 2026 for Shrey. Tools studied: Everything, File Pilot, Files, Directory Opus, Windows Explorer, macOS Finder. Tags: [Certain] = backed by a source in section 11; [Likely] = my inference; [Guessing] = estimate or proposal you must approve.
1. Executive summary
[Certain] The benchmark tools each win on a different axis. Everything wins search speed, File Pilot wins feel, Directory Opus wins power features, and Files wins modern looks plus open-source cloud and Git integration. None wins all four, and none combines instant disk-wide search, content search and a full file manager. [Likely] That gap is where GodXplr can credibly win.
[Certain] Windows Explorer is a moving target. In 2026 Microsoft shipped Explorer speed work, new archive support, a faster Home tab, a search overhaul and a customizable context menu (beta).
Six findings that change the plan:
1. [Certain] File Pilot is fast because it uses no framework: pure C, its own UI toolkit, its own D3D11/OpenGL renderer, no external libraries, one small executable. [Likely] Qt 6 will not match that feel by default, so prompt P04 sets a hard performance gate with a fallback renderer plan.
2. [Certain] Everything is fast because it reads the NTFS Master File Table directly, keeps a compact name table in RAM and follows the USN change journal. This is reproducible but needs a privileged helper service.
3. [Certain] Your MIT choice conflicts with popular libraries: Xapian and poppler are GPL, MuPDF is AGPL, and some Qt modules are GPL-only. The plan uses SQLite FTS5, PDFium, libarchive and Tesseract, and links Qt dynamically.
4. [Likely] An all-drives persistent content index is your most expensive decision. Everything itself keeps content in memory and recommends exclusion filters. GodXplr needs a disk-backed index with caps, exclusions, pause/resume and idle-priority I/O.
5. [Likely] A service running as SYSTEM can leak file names or text to users who lack permission. Content extraction must run as the signed-in user, and name results must be permission-filtered.
6. [Certain] Matching every feature of four mature tools is years of work for their teams. [Likely] The plan keeps every feature in scope but orders it into tiers v1 to v4 with acceptance gates, so something usable exists after each phase.
2. Scope confirmed with you
• Product: GodXplr, a full Windows file manager in C++ with Qt 6, built by Antigravity agents, MIT licensed, for your OS course and portfolio (no required OS topics).
• Platforms: Windows first. macOS and Linux compile in CI only and are labelled unsupported until someone tests them.
• Must beat the others on: UI speed and feel, search speed, power features, Explorer parity (parity is cut last).
• Search: names, contents and smart search (fuzzy, filters, regex, recency/frequency ranking, plus every search function of the benchmark tools). No AI, no paid services. Content index covers all NTFS drives, persistent, every file type with extractable text.
• Privilege: helper service for the NTFS index.
• Shell: real Windows context menu, everyday users, minimal and fast look, default-Explorer replacement in a later phase.
• Distribution: installer and portable from day one.
• Proposed by me, not chosen by you (veto any): Qt Widgets with a custom file view, SQLite FTS5, PDFium, libarchive, Tesseract, Lua scripting, Inno Setup, per-user content process.
3. Teardown of the benchmark tools
3.1 Everything (voidtools): best at filename search speed
• [Certain] It reads the NTFS Master File Table directly and follows the USN journal for live updates. The database is a list of UTF-8 names, sizes, modified dates and parent pointers, held in memory, saved on exit and restored at launch. It is written in C. One write-up reports a fresh Windows 10 install (about 120,000 files) indexing in roughly one second.
• [Certain] Version 1.5 entered beta in May 2026. It adds property indexing and sorting, natural sort, an index journal, Everything Server, a duplicate finder, virtual-folder indexing, an undo system, FAT indexing, dark mode, background updates and weighted searches.
• [Certain] Content indexing exists in 1.5 but the developer describes it as a hidden advanced feature with limited support. Content is stored in memory, default types are doc, docx, pdf, txt, xls and xlsx, it uses the system IFilter, and exclusion filters are advised for performance.
• Weak spots: [Certain] non-NTFS volumes are indexed by slower scanning. [Likely] It is a search tool, not a file manager, and its content search does not scale to every file on every drive.
3.2 File Pilot: best at interface feel
• [Certain] Written in C since full-time work began in 2022, with its own platform layer, renderer (D3D11 and OpenGL), UI framework, containers, string and math code, and essentially no external libraries. It ships as a single small executable (about 2 MB) with no background services and an optional built-in installer. One developer. Perpetual licence.
• [Certain] Interface rendering moved to Direct3D in March 2026. Beta v0.8.1 (July 2026) added tree view, list view, group-by sections and per-folder view settings.
• Features seen: command palette, inspector pane, Go To search, batch rename, bookmarks, recents tracking, thumbnail-loading control, volume usage bars, reopen closed tabs, set-as-default through the installer, drag from ZIP and from external apps, and a Windows 10 style context menu with no 'show more options' step.
• [Certain] Roadmap items: virtual folders, MTP devices, undo/redo, network share reliability, cloud-synced folder status, in-app updates, translations. Listed as future: NTFS file-table indexing, custom Quick Access groups, ARM.
• Weak spots: [Certain] NTFS-table search is still on the roadmap, so its disk-wide search is not Everything-class, and an early beta lacked network browsing. [Likely] No content search, scripting or FTP.
3.3 Files: best at modern UI and open-source integration
• [Certain] Open-source WinUI/Fluent file manager. v4.0 introduced the Omnibar, dual pane, a Status Center, many cloud-drive integrations and clone-on-drop for GitHub URLs. Later releases add a details pane, 7z and compression options, on-demand folder size and network-discovery hints. Version 4.2 shipped in 2026.
• Weak spots: [Likely] user comments report slower startup and sluggishness compared with File Pilot (anecdotal, not measured).
3.4 Directory Opus: best at power features
• [Certain] Native multi-threaded 64-bit C++ with speed as the first design principle. Explorer Replacement mode, single or dual file displays with folder trees, tabs, viewer pane, metadata pane (view and edit EXIF, MP3, PDF tags), batch rename with a macro recorder and scripted rename, FTP plus ZIP/7z/RAR browsed like folders, synchronize, duplicate finder, colour coding, status icons, star ratings, tags, descriptions, collections, saved layouts, folder formats, a scripting interface with scriptable dialogs, and high-DPI support. First released in 1990 as an Amiga two-panel manager.
• Weak spots: [Likely] steep configuration curve, paid upgrades (Opus 13 uses an upgrade-subscription model on a perpetual licence), closed source, and no MFT-style instant index.
3.5 Windows Explorer (state in Nov 2026)
• [Certain] 2026 changes: performance work in KB5095093 (optional in June, mandatory in July), a Home-tab fix, a dark-mode white-flash fix, new archive support, a speed and relevance overhaul for search across This PC, faster large-file deletion, a WinUI 3 Properties dialog, and a customizable context menu in Beta build 26220.9757. Windows 11 26H2 began rolling out in September 2026.
• [Likely] The parity baseline keeps moving, so parity checks must be re-run before release.
3.6 macOS Finder (reference only, not a target platform)
• [Certain] Icon, list, column and gallery views; Quick Look on Space; tags; Smart Folders; tabs; a Tahoe Spotlight overhaul with a file-search mode, filters and previews; custom folder colours and emoji. Column view has no sidebar tree.
• Worth copying: Quick Look style instant preview, Smart Folders, gallery view.

5. Technical findings
5.1 Why Everything is fast, and what to copy
[Certain] Direct MFT read, an in-memory name table, and USN journal tailing. [Likely] GodXplr copies this with a service that opens each NTFS volume read-only, enumerates records with the documented FSCTL_QUERY_USN_JOURNAL, FSCTL_ENUM_USN_DATA and FSCTL_READ_USN_JOURNAL controls, and sends compact snapshots plus deltas to the UI process. Non-NTFS volumes and portable mode need a parallel crawler fallback, which is slower (Everything has the same limit).
5.2 Why File Pilot feels instant, and what Qt costs
[Certain] File Pilot has no framework between it and the OS. [Likely] Qt adds overhead from widget and event machinery, UTF-16 string conversions, model/view signals and per-row shell calls. Tactics that close most of the gap (all [Likely]):
• A custom flat item model with names in an arena, no per-row QObject, uniform row height, painting only visible rows.
• Enumeration with FindFirstFileExW using the basic-info level and large fetch, on worker threads, streaming results into the model in batches.
• Folder sizes, counts and metadata computed in the background and applied asynchronously (File Pilot does this too).
• Icons and thumbnails loaded asynchronously from an LRU cache; no shell call on the UI thread.
• Incremental sorting and stable selection while results stream in.
[Certain] Qt's own QFileSystemModel has long-standing reports of freezing and slow sorting on large folders, so it is banned in this project. [Likely] Gate P04: scrolling a 100,000-entry folder must hold 60 fps with no frame over 16 ms. If the gate fails, only the file view is swapped for a Qt Quick or QRhi-rendered component; the model and core stay.
5.3 Native Windows context menu
[Certain] The shell exposes IContextMenu, IContextMenu2 and IContextMenu3, and owner-drawn items require forwarding menu messages (HandleMenuMsg2). [Likely] Plan: get IContextMenu from the item's IShellFolder (or SHCreateDefaultContextMenu), call QueryContextMenu into an HMENU, show it with TrackPopupMenuEx on the top-level window, forward WM_DRAWITEM, WM_MEASUREITEM and WM_MENUCHAR from a Qt native event filter, then InvokeCommand with the Unicode info structure. [Certain] File Pilot shows the classic Windows 10 style menu with no 'show more options' step. [Likely] That is the achievable meaning of 'real Windows menu' for an unpackaged app. Third-party handlers can hang or crash, so calls need a watchdog and the UI must survive a bad handler.
5.4 Search engine design
• Names: in-memory arrays with parent pointers, case-folded copies, per-column sort orders, and result reuse when a query only extends the previous one. [Likely]
• Syntax: a superset of Everything's operators (space = AND, | = OR, ! = NOT, quotes, wildcards, regex:, size:, dm:, dc:, da:, ext:, path:, content:, case:, wholeword:). [Likely]
• Fuzzy: subsequence scoring in the style of fuzzy finders plus edit-distance 1 for short tokens. Ranking = match score + recency + frequency from a local usage database. [Likely]
• No AI, no network, no cost, as you required.
5.5 Content index design
• Storage: SQLite FTS5 with the trigram tokenizer gives substring and phrase search with no server. [Likely] Tantivy (Rust, permissive) is the alternative but adds a second toolchain. [Certain] Xapian is a good C++ engine but GPL, so it is rejected.
• Pipeline: USN change feed, then an extraction queue, then extractor plugins, then one FTS5 shard per volume, then merged queries. [Likely]
• Extractors: text and code with encoding detection; OOXML (docx, xlsx, pptx) through zip plus XML parsing; PDF through PDFium; archives through libarchive (zip, 7z, rar read, searching member text); OCR through Tesseract for images and scanned PDFs as the last tier. Video, encrypted and binary files get name and metadata only, so 'everything' means every file with extractable text. [Likely]
• Controls: exclusion rules (system folders, build output, VCS internals), per-file size cap, per-type toggles, pause on battery, idle I/O priority, resume after a crash, and an up-front size and time estimate. Content lives on disk, not in RAM. [Likely]
• [Guessing] Index size will land somewhere between 20% and 60% of the indexed text volume. We measure it in P11 before promising anything.
5.6 Helper service and security
• [Likely] The service uses the least privilege that lets it open volume handles read-only, accepts clients over a named pipe whose access list admits only interactive users, serves metadata only, and never offers arbitrary file reads.
• [Likely] Visible search rows are permission-checked as the caller, so the service cannot show a user names they cannot see.
• [Likely] Content extraction runs in a per-user background process, so a user's content index only holds files that user can read.
• [Likely] Portable mode has no service, so it uses the in-process crawler and ReadDirectoryChangesW.

5.8 Default-Explorer replacement
[Certain] Directory Opus, File Pilot (installer option since January 2026) and Files can act as the default folder opener. [Likely] The mechanism is registry verbs for folders, drives and the Win+E shortcut, which Windows updates can break. It stays in the last tier, fully reversible, with a one-click restore.
